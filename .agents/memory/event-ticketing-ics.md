---
name: Event ticketing on the ics link type
description: Paid ticket tiers/QR/check-in built on top of the free-RSVP `ics` calendar link type — where the surfaces live and naming gotchas.
---

The `ics` link type (mobile kind label `"calendar"`) grew paid ticketing: `EventTicketTier`/`EventTicket` models, `MonetizationCheckout`'s `event_ticket` kind (0% platform fee, reuses the existing creator-payout system), a public `/events` directory + `/{alias}` event page, owner tier CRUD + QR check-in scanner (web), and full `/api/v1` mobile parity (`EventTicketApiController`) + mobile screens under `app/events/*`.

**Why paid and free RSVP coexist safely:** ticketing is opt-in per event (`ticketing_enabled` / `tiers` presence); the original free-RSVP flow is untouched code paths.

**How to apply / gotchas:**
- The owner check-in endpoint path is `/api/v1/links/{link}/event-checkin`, NOT under `/events/{id}/checkin/*` — it lives with the other per-link owner actions, not the public events namespace. Don't guess the path; grep `routes/api.php` before wiring a client.
- Mobile ticketing entry point is gated on `meta.kind === "calendar"` (not `"ics"` or `"event"`) in `app/links/[id]/edit.tsx`'s kind mapping (`lib/linkKinds.ts`).
- Adding new Expo Router screens (e.g. `app/events/...`) breaks `router.push()` typecheck until `.expo/types/router.d.ts` is regenerated. If no expo dev workflow is currently running, a one-off `timeout 25 npx expo start --no-dev --offline --port <free-port>` inside the mobile package regenerates the types file well enough for `tsc --noEmit` to pass — no need for a live full dev server.
- `composer check:mobile-docs-parity` only tracks *link/block type* documentation drift, not fine-grained sub-features like ticketing; a new sub-feature on an already-documented link type won't show as drift.
- **Offline ticket display:** the mobile ticket QR screen (`app/events/ticket/[alias]/[code].tsx`) caches the fetched `FullEventTicket` (incl. `qr_svg`) in AsyncStorage keyed per `(alias, code)` (`getEventTicket` writes it), and falls back to `getCachedEventTicket` **only on a network-class failure** (`errorStatus(e) === null`, i.e. `fetch` rejected with no HTTP status) so the QR still shows at a venue with poor signal — a server error (404/410 for a deleted ticket) must surface, not a stale saved QR. **Invalidation rule:** a `refunded`/`cancelled` status drops the cache instead of storing it — a stale QR must never keep letting a refunded attendee in.
- **Live door check-in progress** (real-time counter for organizers) is `App\Services\Events\EventCheckinProgress::for(Link)` → `{totals:{sold,checked_in,remaining}, tiers:[…], updated_at}`. Surfaced on web (`user.links.ics.checkin.progress`), API (`GET /links/{link}/event-checkin/progress`), and mobile (`getCheckinProgress` in `lib/api/events.ts`), all polled every 5s. **Counting semantics gotcha:** the service counts by summed ticket `quantity` (`SUM(quantity) FILTER (WHERE status=...)`) for BOTH sold and checked_in — deliberately consistent. The pre-existing owner-totals surfaces (`EventTicketTierController::index`, API `ownerTiers`) instead compute `checked_in` as a *row count* while `sold` is a quantity sum, so their two numbers aren't directly comparable. When adding another totals surface, match the quantity-sum-for-both convention, not the older mixed one.

**Owner ticket refunds:** `MonetizationCheckout::refundEventTicket(int $id, ?string $reason)` is the single funnel (reuses creator-payout/coin-wallet plumbing, 0% fee). Double-refund idempotency = a `DB::transaction`+`lockForUpdate` status claim (skip if already `refunded`/`cancelled`); the gateway reversal runs *outside* the lock. On success it flips status, decrements the tier `sold_count` (frees the seat), writes the negative ledger event, and calls `notifyAttendeeOfTicketRefund()` (email via `Emailer::send('ticketing.refunded', attendee_email, ...)` + a `ticket.refunded` UserNotification for registered buyers, deep-linked to `redirect.event.ticket` — there is no `user.events.mine` route). Check-in already rejects refunded tickets on both web (`EventCheckinController`) and API (`EventTicketApiController::checkin`); the offline-cache invalidation rule above also drops a refunded ticket's cached QR.
- Surfaces: web refund button in `event-tickets.blade.php` "Recent tickets" (only for `valid`/`checked_in`) → `EventTicketTierController::refundTicket` (route `user.links.ics.tickets.refund`); API `POST /api/v1/links/{link}/event-tickets/{ticket}/refund` + owner list `GET /api/v1/links/{link}/event-tickets` (`ownerTickets`/`refundTicket`); mobile `refundEventTicket`/`getOwnerTickets` in `lib/api/events.ts` + "Recent tickets" list on `app/events/tiers/[linkId].tsx`.
- New `ticketing.refunded` key added to `EmailTemplateRegistry` (category `events`).
